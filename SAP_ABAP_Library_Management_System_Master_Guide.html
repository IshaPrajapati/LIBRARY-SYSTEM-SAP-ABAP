4. 🖥️ Screen-by-Screen Flow & Business Logic

Screen 1000: Authentication (Login)

  • PBO: Initializes screen parameters, clears credentials.
  • PAI: Triggers on OK-Code 'LOGIN'. Queries ZA16_L_LOGIN:
SELECT SINGLE * FROM za16_l_login INTO wa_login
  WHERE user_id = user_id AND password = password.
IF sy-subrc = 0.
  stu_id = wa_login-stu_id.
  CALL SCREEN 1001.
ELSE.
  MESSAGE 'ENTER THE CORRECT VALUE' TYPE 'I'.
ENDIF.

Screen 1001: Central Dashboard & Navigation Dispatcher

  • PBO: Dynamic welcome banner. Queries student name from ZA16_L_INFO using active STU_ID.
  • PAI: Dispatches to modules based on button clicked:
    • 'SEARCH' ➔ CALL SCREEN 1004 (Search Books)
    • 'GET' ➔ CALL SCREEN 1005 (Issue Book)
    • 'RETURN' ➔ CALL SCREEN 1006 (Return Book)
    • 'SHOW' ➔ LEAVE TO SCREEN 1007 (Active Borrowings)
    • 'UPDATE' ➔ CALL SCREEN 1008 (Update Profile)
    • 'LOGOUT' ➔ CALL SCREEN 1000

Screens 1002 & 1003: Two-Step Student Registration

  • Screen 1002 (Credentials): Validates password confirmation (pass = pass2). Auto-generates student ID via SELECT MAX( stu_id ), commits to ZA16_L_LOGIN, and calls Screen 1003.
  • Screen 1003 (Demographics): Collects gender via radio buttons, academic degree, branch, address, roll number, and sets timestamp. Commits to ZA16_L_INFO.

Screen 1004: Catalog Search with Table Control LIB1

  • Table Control Declaration: CONTROLS: lib1 TYPE TABLEVIEW USING SCREEN 1004.
  • PBO Flow: 
    MODULE lib1_init OUTPUT.
  IF g_lib1_copied IS INITIAL.
    SELECT * FROM za16_l_book_info INTO CORRESPONDING FIELDS OF TABLE g_lib1_itab.
    g_lib1_copied = 'X'.
    REFRESH CONTROL 'LIB1' FROM SCREEN '1004'.
  ENDIF.
ENDMODULE.

MODULE lib1_move OUTPUT.
  MOVE-CORRESPONDING g_lib1_wa TO za16_l_book_info.
ENDMODULE.
  • Allows pagination (P+, P-, P++, P--) and scrolling.

Screen 1005: Book Issuance Engine

  • Business Rule Validation: Prevents duplicate borrowing of the same title: 
    SELECT SINGLE * FROM za16_l_getbook INTO gg_book WHERE stu_id = stu_id.
IF gg_book IS NOT INITIAL AND gg_book-book_id = bk_id.
  MESSAGE 'THE BOOK ALREADY EXISTS TO YOU' TYPE 'I'.
ELSE.
  " Auto-increment GET_ID and write loan record
  INSERT za16_l_getbook FROM wa_get.
ENDIF.
  • Uses sy-datum date slicing: cr_dat2+0(4) (Year), cr_dat2+4(2) (Month), cr_dat2+6(2) (Day) concatenated into DD/MM/YYYY.

Screen 1006: Return & Settlement

  • Fetches loan record by GET_ID. Displays book details, loan date, and calculated return date.
  • Settles loan by executing: DELETE FROM za16_l_getbook WHERE get_id = bk_id2.

Screen 1007: Inner Join Active Borrowings (Table Control EDWR)

SELECT za16_l_info~stu_id, za16_l_info~user_id, za16_l_info~name,
       za16_l_info~roll, za16_l_info~field, za16_l_info~date_and_time,
       za16_l_getbook~get_id, za16_l_getbook~book_id,
       za16_l_getbook~author, za16_l_getbook~car_date
  INTO CORRESPONDING FIELDS OF TABLE it_join
  FROM za16_l_info INNER JOIN za16_l_getbook
    ON za16_l_info~stu_id = za16_l_getbook~stu_id
  WHERE za16_l_info~stu_id = stu_id.

5. 🎯 Top 20 Real Interview Questions & Expert Answers

Dynpro Q1: What type of program is this, and how is it executed?
This is a Module Pool Program (Type M). Unlike executable reports (Type 1) that begin with START-OF-SELECTION, module pool programs cannot be executed via F8 in SE38. They require a Transaction Code (T-Code) created in transaction SE93, pointing to program ZA16_LIBRARY_MANAGEMENT and initial screen 1000.
Dynpro Q2: What is the purpose of SY-UCOMM and why should it be cleared?
SY-UCOMM is a system field holding the function code triggered by the user's interaction (pushbutton, Enter, menu item). We bind a screen field (often OK_CODE) to it. After processing in PAI, both OK_CODE and SY-UCOMM must be cleared (CLEAR ok_code; CLEAR sy-ucomm;) to avoid re-triggering the same action unintentionally on subsequent screen passes or Enter clicks.
Navigation Q3: What is the exact difference between CALL SCREEN and LEAVE TO SCREEN?
  • CALL SCREEN <nnnn>: Pushes the current screen onto SAP's internal screen stack (up to 50 levels deep) and initiates a new screen sequence. Returning is done via LEAVE TO SCREEN 0, which restores the previous screen's context.
  • LEAVE TO SCREEN <nnnn>: Replaces the current screen at the same stack level without nesting. Control does not automatically return back when done.
Table Control Q4: How does a Table Control work in Dynpro flow logic?
In the screen painter, a Table Control is linked to a declared control (CONTROLS tc TYPE TABLEVIEW USING SCREEN ...).
In PBO, we loop through the internal table with control (LOOP AT itab INTO wa WITH CONTROL tc) to transfer data line-by-line to the screen fields for visible lines (governed by SY-LOOPC).
In PAI, a corresponding LOOP AT itab receives any user input or selection flags modified on screen and updates the internal table.
DDIC Q5: Why is MANDT the first primary key in all 4 custom tables?
MANDT (Client, data type CLNT) makes the table client-dependent. In SAP multi-tenant architecture, multiple business clients (e.g., Client 100 for Development, 200 for QA) share the same database. The ABAP Open SQL runtime automatically filters queries by the user's active client (sy-mandt), guaranteeing complete data isolation across clients.
Open SQL Q6: Why did you use SELECT SINGLE for login and not UP TO 1 ROWS?
SELECT SINGLE is designed for queries where the complete primary key is specified in the WHERE clause. The database retrieves the exact unique record directly without creating a cursor. UP TO 1 ROWS is intended for searching when the full primary key is not provided and multiple rows could match.
Performance Q7: Why should SELECT ... ENDSELECT be avoided in production SAP systems?
SELECT ... ENDSELECT executes a row-by-row cursor loop across the network between the application server and the database, leading to high latency and database bottlenecks. The standard SAP best practice is Array Fetching: SELECT ... INTO TABLE <itab>, which retrieves records in bulk packets.
Advanced ABAP Q8: What are Field Symbols and why were they used in your Table Control subroutines?
Field Symbols (e.g., FIELD-SYMBOLS <tc> TYPE cxtab_control) are typed symbolic pointers to existing memory areas, analogous to pointers in C/C++. In the generic table control routine user_ok_tc, they allow dynamically assigning and manipulating any table control structure and mark columns (ASSIGN (p_tc_name) TO <tc>) at runtime without creating redundant memory copies.
Error Handling Q9: How do message types 'E', 'I', and 'S' differ in SAP Dynpro?
  • TYPE 'E' (Error): Displays in the status line, turns input fields in error red, lock fields, and interrupts PAI until valid input is supplied.
  • TYPE 'I' (Information): Displays a modal dialog pop-up. Once the user clicks Enter, execution continues uninterrupted.
  • TYPE 'S' (Success): Displays a green checkmark confirmation in the status bar on the subsequent screen without halting execution.
Architecture Q10: How would you modernize this project for SAP S/4HANA?
1. Replace classic Dynpro screens with modern SAP Fiori / SAPUI5 responsive web apps.
2. Build ABAP Core Data Services (CDS) Views to push data join and validation logic down into the in-memory SAP HANA database engine.
3. Expose backend services via OData v2 / v4 using the ABAP RESTful Application Programming Model (RAP).
4. Replace manual sequence generation (SELECT MAX) with SAP Number Range Objects (SNRO) and function module NUMBER_GET_NEXT.
